# Как разобраться в проекте

Начните с запуска приложения и пройдите сценарий из README. Затем прочитайте
`Ticket`, `DeskService`, `TicketController` и интеграционные тесты в таком порядке.

## Что здесь важно понимать

**Зачем DTO, если уже есть Entity?**
Entity описывает хранение данных и связи JPA. DTO описывает запрос и ответ HTTP.
Это позволяет не отдавать внутренние связи наружу и отдельно валидировать ввод.

**Где транзакция?**
В методах `DeskService`. Загрузка заявки, проверка правила и запись изменения
происходят в одной транзакции. Ошибка приводит к откату.

**Почему нет save после каждого изменения?**
JPA отслеживает изменения управляемых сущностей (dirty checking).
`flush()` отправляет UPDATE до построения ответа, чтобы вернуть новую `version`.
Это ещё не commit: фиксация происходит при завершении транзакции.

**Зачем Flyway?**
Схема хранится в версионируемых SQL-миграциях.
Hibernate только проверяет соответствие сущностей схеме, а не меняет её автоматически.

**Почему есть проверки и в Java, и в SQL?**
Java возвращает понятную бизнес-ошибку. Ограничения БД защищают целостность
даже при конкурентных запросах или записи в обход приложения.
Например, предварительная проверка email не заменяет UNIQUE в БД.

**Как работает @Version?**
Hibernate включает версию в условие UPDATE и увеличивает её.
Если другую транзакцию уже зафиксировали, обновлено ноль строк — возникает
ошибка оптимистической блокировки. API возвращает 409.
Для обнаружения изменений между двумя отдельными действиями пользователя
нужно дополнительно передавать ожидаемую версию, например через If-Match.

**Почему EntityGraph?**
У заявки лениво загружаемый инженер. При обходе списка без явной загрузки
можно получить отдельный SQL-запрос на каждого инженера.
EntityGraph запрашивает связь сразу; пагинация безопасна для этой связи ManyToOne.

**Почему нет удаления заявок?**
Тикеты и комментарии составляют историю поддержки. В этой версии нет операций
удаления или редактирования истории. Архивацию можно добавить отдельно.

**Что тестируется?**
Unit-тесты проверяют правила сущности без БД.
Интеграционные тесты поднимают Spring и настоящий PostgreSQL, применяют миграции
и отправляют HTTP-запросы через MockMvc. Проверка блокировки использует
две независимые транзакции.

## Небольшие самостоятельные улучшения

1. Добавьте приоритет LOW / MEDIUM / HIGH через миграцию V2, DTO и фильтр.
2. Добавьте тесты для нового фильтра и некорректного значения приоритета.
3. Добавьте журнал смены статусов с предыдущим и новым статусом.
4. После этого попробуйте Spring Security и получение автора из текущего пользователя.

На собеседовании полезнее разобрать один запрос от контроллера до SQL и объяснить
его ограничения, чем перечислить названия библиотек.
